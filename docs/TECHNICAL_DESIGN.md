# Technical Design Document

## 1. Purpose and boundaries

OcuPulse is an experimental data-acquisition and signal-analysis prototype. It explores whether repeatable features can be extracted from ToF distance and PPG signals. It **does not directly measure IOP**. The current repository has no IOP calibration coefficients and intentionally does not calculate or display a clinical IOP estimate.

## 3. Hardware interfaces

| Device | Interface | Default connection | Data |
|---|---|---|---|
| ESP32 DevKit V1 | Controller | — | timestamps, serial logging |
| VL53L1X | I2C | SDA 21, SCL 22 | range in mm, status/validity |
| MAX30102 | I2C | SDA 21, SCL 22 | raw IR sample count |
| SSD1306 OLED (optional) | I2C | SDA 21, SCL 22 | simple status display |

Sensor modules share the I2C bus, so their addresses must not conflict. Confirm exact breakout board voltage and pin requirements.

## 4. Acquisition and synchronization

The firmware emits event rows with the schema event,timestamp_us,value,valid. TOF events carry a distance in millimetres; PPG events carry an IR count. The two sensor clocks are read using the ESP32 microsecond timer, but the acquisition events are **not simultaneous**. Downstream research must retain timestamps and document how channels are aligned or resampled. Do not pair samples just because each sensor has a nominal sampling frequency.

The VL53L1X is configured for a nominal 20 ms continuous-ranging period and 20,000 µs timing budget in the sketch. The PPG stream is configured separately; effective output cadence must be verified on the physical board. OLED refresh is intentionally slow to reduce bus contention.

## 5. Signal-processing methods

For a paired, explicitly aligned offline series, the Python helpers provide:

1. Global-threshold local maximum detection with a minimum peak separation.
2. Approximate average heart rate, HR = 60 / mean(RR), where RR is the inter-peak time in seconds.
3. Exploratory local distance range around each PPG peak: OPA_proxy = max(D_window) - min(D_window).
4. A local rise/fall time ratio when valid before/after extrema exist.
5. A sample-index delay converted to milliseconds.

These features are algorithmic proxies only. Filtering, baseline removal, event alignment, signal quality, physiological confounding, and peak selection require careful evaluation before using real research data.

## 6. Sample-data policy

The included CSV is synthetic test data generated by a simple script. It is not collected from a person and is not evidence of sensor performance. Do not include identifiable or unapproved human data in a public repository.

## 7. Verification and validation

- Software unit tests verify simple synthetic conditions and input validation.
- Bench-test ToF against a fixed, non-human target and calibrated displacement reference.
- Characterize mean, bias, standard deviation, repeatability, valid-reading rate, and Allan deviation over justified durations.
- Validate PPG peak detection against manually annotated or a suitable reference signal before making performance claims.
- Keep sensor characterization, exploratory physiological studies, and clinical validation as distinct stages.
- Any clinical IOP model requires properly governed reference measurements, subject-level data splits, pre-specified evaluation, uncertainty estimates, and independent assessment. Do not use the current feature code as a clinically validated model.

## 8. Risk register

| Risk | Mitigation |
|---|---|
| ToF sensor may not resolve required small displacement | Quantify displacement sensitivity and noise on controlled non-human targets before any physiological interpretation. |
| Reflectance, alignment and ambient light affect the return | Use controlled geometry and document target/optical conditions. |
| PPG motion artefacts or weak signal | Add signal-quality flags and reject unsuitable captures. |
| Timing mismatch between channels | Preserve timestamps; document resampling and account for offsets. |
| Small data set / overfitting | Keep participant-level separation and independent testing. |
| Users may mistake output for a diagnosis | Do not produce a clinical IOP value; clearly label output experimental. |
| Eye-safety / human subject risk | Do not aim at human eyes without optical-safety assessment, ethics review where required, and qualified clinical oversight. |

## 9. Open questions to resolve

- Exact sensor breakout board versions and power specifications.
- Actual installed Arduino/ESP32 and sensor-library versions.
- Measured sample cadence and dropped-sample rate on hardware.
- Validated method for time alignment and signal-quality screening.
- Whether a controlled displacement experiment demonstrates adequate system sensitivity.
